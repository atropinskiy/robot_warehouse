# Sim-engine: серверный движок, события и цикл

Статус: согласуемая модель. Этот документ описывает протокол событий и цикл движка; [диспетчер](dispatcher.md) и [робот](robot.md) описаны отдельно.

## Ответственность

Sim-engine включает диспетчер, XState-акторов роботов, поиск пути и разрешение конфликтов. Диспетчер разрешает движение, актор робота самостоятельно изменяет свою позицию после разрешения. Runner задаёт темп вызовами `tick()`, публикует результат и передаёт события на сохранение. Внутри движка нет HTTP, БД, WebSocket и таймеров реального времени.

## Выполнение на бэкенде

Весь описанный функционал выполняется на бэкенде в Node.js: планировщик, логическое время, `tick()`, диспетчер, XState-акторы роботов, очередь намерений, маршрутизация, разрешение конфликтов и обслуживание на станциях. Отсутствие NestJS и сетевого кода внутри движка означает отделение доменной логики от серверных адаптеров, а не выполнение в браузере.

`packages/sim-engine` — внутренний пакет, используемый бэкендом. NestJS-модуль симуляции создаёт экземпляр движка и `SimulationRunner`. Для одного запуска диспетчер и все роботы работают в одном серверном процессе; внутренние сообщения акторов не проходят через WebSocket или Redis.

Акторы роботов принадлежат долгоживущему серверному реестру, который инициализируется при старте процесса и существует независимо от запусков симуляции. Движок использует ссылки на эти акторы. `robot.stop`, завершение задания и сброс запуска не прекращают их работу. Во время работы процесса актор удаляется только специальной операцией `robot.delete`, удаляющей соответствующего доменного робота; правила описаны в [модели робота](robot.md#жизненный-цикл). При добавлении робота после старта процесса создаётся новый актор.

```text
Фронтенд: пользовательская команда
    → HTTP/WebSocket API бэкенда: проверка прав и входных данных
    → серверный runner инстанса-владельца
    → sim-engine: диспетчер ↔ акторы роботов
    → runner: снимок/изменения и события
    → WebSocket: отображение на фронтенде
    → серверные адаптеры: Redis / PostgreSQL / уведомления
```

При нескольких инстансах бэкенда один склад обрабатывает только инстанс-владелец. Команды с других инстансов перенаправляются владельцу; Redis используется для межсерверной координации, распространения обновлений и актуального снимка. Он не заменяет внутреннюю очередь намерений. Проверка прав выполняется на инстансе, принимающем пользовательскую команду.

Фронтенд отправляет пользовательские команды, отображает полученные состояния, маршруты и события и анимирует переходы между серверными координатами. Он не вызывает `tick()`, не рассчитывает разрешения на шаг и не запускает акторов симуляции. Если типы DTO вынесены в общий пакет, это не переносит исполнение движка на клиент.

Закрытие браузера не останавливает серверный запуск. После переподключения клиент получает актуальный снимок. При падении процесса допускается отметить запуск прерванным; автоматическое восстановление акторов и продолжение тика не входит в базовые требования.

## Общие типы

События XState описываются объектами с обязательным строковым полем `type` и дополнительными полями данных. В проекте принято именование через точки: `<область>.<действие или факт>`, например `robot.move.completed`. Это соглашение проекта, совместимое с [форматом событий XState](https://stately.ai/docs/transitions#event-objects); XState не требует конкретного регистра или разделителя.

Команды называются действием (`robot.task.assign`, `robot.pause`), результаты — фактом (`robot.task.accepted`, `robot.move.completed`). События отдельного робота имеют префикс `robot`, управления запуском — `simulation`, событий диспетчера — `dispatcher`. TypeScript-типы сохраняют PascalCase: `MoveCompletedEvent`.

```ts
type Position = { x: number; y: number };
type RobotId = string;
type TaskId = string;
type StationId = string;
type RunId = string;
type TickId = number;
type CommandId = string;

type MoveIntent = {
  tickId: TickId;
  runId: RunId;
  robotId: RobotId;
  assignmentVersion: number;
  from: Position;
  to: Position;
};

type MoveDecision = {
  runId: RunId;
  tickId: TickId;
  robotId: RobotId;
} & (
  | { type: "robot.move.granted" }
  | {
      type: "robot.move.denied";
      reason: "occupied" | "reserved" | "headOn" | "invalid";
      blockingRobotIds: RobotId[];
    }
);
```

Координаты целочисленные, переход разрешён только между четырьмя соседями. `runId` отделяет сообщения разных запусков, `tickId` — разных циклов, `assignmentVersion` меняется при замене маршрута или назначения.

## Входные команды и события акторов

Внешние команды: `task.create`, `simulation.pause`, `simulation.resume`, `simulation.stop`, `robot.pause`, `robot.resume`, `robot.stop`, `robot.break`, `robot.repair`. Каждая команда содержит `commandId` и `runId`; параметры зависят от типа. Команды `robot.*` дополнительно адресованы конкретному `robotId`; команды `simulation.*` управляют всем запуском, а диспетчер передаёт соответствующие события акторам. Сброс создаёт новое исходное состояние с новым `runId`.

Сброс сохраняет существующие экземпляры акторов и через отдельный переход сброса устанавливает исходную позицию, очищает назначение, намерения и отметки тиков прежнего запуска. `robot.delete` — отдельная команда жизненного цикла с `commandId` и `robotId`, не привязанная к `runId`. Остановка запуска не вызывает удаление роботов.

Диспетчер отправляет роботу:

| Событие | Назначение |
|---|---|
| `robot.task.assign` | Предложить назначение |
| `robot.route.replace` | Заменить маршрут внутри назначения |
| `robot.move.granted` / `robot.move.denied` | Ответить на конкретное намерение |
| `robot.break` / `robot.repair` | Изменить работоспособность |
| `robot.pause` / `robot.resume` | Изменить режим исполнения |
| `robot.service.advance` | Продвинуть погрузку или выгрузку на один логический тик |

Робот отправляет диспетчеру:

| Событие | Назначение |
|---|---|
| `robot.task.accepted` / `robot.task.rejected` | Результат принятия назначения |
| `robot.route.accepted` / `robot.route.rejected` | Результат замены маршрута |
| `robot.move.intent` | Самостоятельно сформированное предложение следующего шага в очередь управления |
| `robot.move.completed` / `robot.move.rejected` | Результат применения разрешения |
| `robot.pickup.completed` | Погрузка завершена |
| `robot.task.completed` | Выгрузка и задание завершены |
| `robot.broken` / `robot.repaired` | Изменение работоспособности |

Подтверждения команд содержат `commandId`; результаты движения — `runId`, `tickId`, `robotId`. Дубли не должны повторно менять состояние.

## Очередь намерений

Актор сам отправляет `robot.move.intent`, когда имеет маршрут, может двигаться и не ожидает решения предыдущего намерения. Команды подготовки шага и опроса намерений нет. Статус публикуется при смене состояния или по запросу диспетчера раз в 100 тиков. События времени сами по себе не требуют публикации; намерение нужно только для начала нового перехода.

Очередь — `Map<RobotId, MoveIntent>`, не более одного ожидающего намерения каждого робота. Повтор того же `tickId` игнорируется, другое намерение при уже ожидающем отклоняется. Проверяются регистрация робота, запуск, позиция и версия назначения. Номер тика не переиспользуется в течение жизни актора.

В начале тика диспетчер атомарно отделяет текущий набор от очереди новых намерений. После результата предыдущего намерения робот ждёт следующего события времени. Намерение другого или просроченного тика отклоняется. Очередь и текущий набор ограничены числом роботов каждый. Это не ограничивает автоматически очередь внешних команд или mailbox.

## Цикл данных

1. Общие часы продвигают тик. Диспетчер применяет управляющие команды, runtime доставляет завершения ранее разрешённых переходов. Внутренний robot.tick используется для подготовки следующего шага, но не для обязательной публикации состояния.
2. Роботы отправляют статусы только при смене состояния, а при готовности к новому шагу — намерения в очередь. В moving не требуется новое намерение или статус на каждом тике.
3. Каждые 100 общих тиков диспетчер отправляет всем роботам robot.status.request с robotId и тиком опроса; отдельно контролирует срок получения ответа. Ответ требуется даже при неизменном состоянии.

   При новом задании или отмене существующего диспетчер может отправить такой запрос вне очереди соответствующим роботам. Плановый график сохраняется; совпавшие запросы объединяются по правилам очереди диспетчера. Отмена выполняется отдельной командой управления, а не запросом статуса.
4. Диспетчер обрабатывает поступившие события, проверяет согласованность и сроки ответов и движения. Отсутствие сообщений на обычном тике не является ошибкой. Отсутствие намерения после фазы подготовки у готового робота запускает проверку; для moving проверяется срок перехода.
5. Диспетчер фиксирует набор намерений, проверяет конфликты и резервирует источник, цель и переход. Выдаёт не более одного нового разрешения роботу за тик.
6. Робот по разрешению переходит в moving. Координата и маршрут меняются только при фактическом прибытии robot.waypoint.reached; затем отправляется robot.move.completed и статус нового состояния. Резервации сохраняются между тиками до обработки подтверждения.
7. Обновляются задания, журнал и публичное состояние. Незавершённые переходы и ожидаемые ответы на опрос остаются в данных диспетчера для следующих тиков; цикл не ждёт их завершения в том же тике.

Тики продолжаются при паузе запуска для контроля движения и периодического опроса; новые разрешения при паузе запрещены. Дедупликация очередей и доставки остаётся ответственностью диспетчера. При ошибке новые разрешения приостанавливаются, занятость и резервации сохраняются; начатые переходы не отменяются автоматически. Номера тиков не переиспользуются при сбросе. Подробные правила — в [полной модели робота](robot.md#публикация-состояния-и-контрольный-опрос).

## Интерфейс движка для серверного runner

```ts
type SimEngine = {
  enqueue(command: EngineCommand): void;
  tick(): TickOutput;
  getSnapshot(): SimulationSnapshot;
};

type TickOutput = {
  runId: RunId;
  tickId: TickId;
  snapshot: SimulationSnapshot;
  events: SimulationEvent[];
};
```

Это концептуальные типы, а не готовые объявления API. Методы вызываются внутри бэкенда; это не HTTP/WebSocket-контракт для браузера. Экземпляр движка владеет состоянием акторов между вызовами. Для повторяемых тестов используются логические тики, стабильный порядок команд и приоритетов; намерения, сформированные внутренними событиями, обрабатываются в своих фазах, а новые намерения остаются для следующего тика.

## Библиотеки для организации tick()

`tick()` объединяет механику симуляции и правила склада. Библиотека может управлять логическим временем, планированием событий и порядком их выполнения. Назначение заданий, разрешение конфликтов намерений, резервации и обнаружение дедлоков остаются логикой диспетчера.

### Текущий выбор

**Предварительный выбор — `js-simulator` как планировщик событий, XState — для акторов роботов.** Это кандидат для прототипа, а не подтверждённая интеграция: пакет не установлен и совместимость с проектом не проверена. Собственный пакет `packages/sim-engine` сохраняет внешний интерфейс `tick()` и скрывает конкретный планировщик за адаптером.

Причина выбора: ручное продвижение симуляции через `Scheduler.update()`, повторяющиеся события и приоритеты ближе всего к нашей модели явных фаз тика. Один вызов библиотечного `update()` нельзя заранее считать одним полным тиком склада: адаптер должен завершать все фазы нашего тика до возврата результата.

### Сравнение вариантов

| Библиотека | Инструменты и преимущества | Ограничения для нашей модели |
|---|---|---|
| [`js-simulator`](https://github.com/chen0040/js-simulator) | `Scheduler`, ручное продвижение времени через `update()`, разовые и повторяющиеся события, приоритет `rank`. Позволяет явно планировать фазы и продвигать симуляцию в тестах | События одинакового ранга перемешиваются по описанию README. Нельзя полагаться на порядок добавления для воспроизводимости. Требуется проверить порядок фаз, управление паузой и интеграцию с XState |
| [SimScript](https://github.com/Bernardo-Castilho/SimScript) | TypeScript, классы `Simulation` и `Entity`, задержки, сигналы, захват и освобождение ресурсов `Queue`. Удобен для ожидания станции, длительности погрузки и моделирования ограниченной ёмкости | Процессные сценарии через `async/await` могут дублировать поведение XState-акторов. Захват клетки как ресурса не заменяет общую проверку намерений, запрет встречного обмена и стратегию отступления |
| [`simloop`](https://simloop.vercel.app/) | DES для Node.js на TypeScript, типизированные обработчики `sim.on()`, планирование `ctx.schedule()`, логическое время `ctx.clock`, статистика. Подходит как кандидат на событийное ядро | В изученном примере показан `run()`. Ручное продвижение, пауза и приём внешних команд во время работы не подтверждены; требуется исследовать до выбора |

SimScript предпочтительнее, если решим передать библиотеке управление ресурсами и процессами обслуживания. `simloop` интересен типизированным событийным API, если подтвердится возможность управляемого пошагового исполнения. Сейчас `js-simulator` ближе к выбранному протоколу без переноса поведения робота из XState.

### Граница интеграции и проверка кандидата

- Один источник логического времени — планировщик внутри `sim-engine`. Runner задаёт реальный темп, но не создаёт отдельные таймеры для роботов.
- Все рассматриваемые библиотеки используются как серверные инструменты. Браузерные демонстрации и средства анимации библиотек не являются основанием запускать симуляцию на фронтенде; пригодность проверяется для Node.js без DOM.
- Планировщик запускает фазы; диспетчер определяет решения; XState-актор применяет разрешённый шаг и меняет собственную позицию.
- Завершение фазы учитывает обработку сообщений XState: само упорядочивание событий планировщика не гарантирует завершения всех ответов акторов.
- Очередь намерений остаётся ограниченным `Map<RobotId, MoveIntent>` с проверкой одного ожидающего намерения на робота и одного обрабатываемого намерения на тик. Планировщик не обеспечивает это доменное ограничение автоматически.
- До окончательного принятия `js-simulator` нужно проверить работу в Node.js/TypeScript, управление шагом и паузой, порядок событий с одинаковым временем и повторяемость результатов при одинаковых входных командах.

Источники возможностей — документация проектов по ссылкам в таблице. Сравнение основано на чтении документации; проверка выполнения в нашем проекте ещё не проводилась.
