# Мониторинг ошибок frontend

Frontend отправляет ошибки в облачный GlitchTip через SDK `@sentry/nextjs`.

Организация: `robot-warehouse`.
Проект: `robot-warehouse-frontend`.
Адрес сервиса: https://app.glitchtip.com

Текущая интеграция проверена с `@sentry/nextjs` 11.11.0,
Next.js 16.4.5 и Turbopack.

## Что подключено

- Ручная отправка исключений из браузера.
- Сбор необработанных браузерных ошибок.
- Отправка ошибок React-рендера через `error.tsx` и `global-error.tsx`.
- Сбор серверных ошибок Next.js через `onRequestError`.
- Загрузка source maps при production-сборке с токеном.

NestJS и Edge runtime этой интеграцией не охвачены.

Session Replay и sampling транзакций производительности не настроены.

## Как это работает

Мониторинг состоит из двух независимых процессов.

### Отправка ошибок во время работы приложения

Приложение использует DSN, чтобы отправлять события в frontend-проект GlitchTip.

Браузерный SDK запускается до гидратации React.
Серверный SDK инициализируется при запуске экземпляра сервера Next.js.

Ошибки, перехваченные нашими React error boundaries,
отправляются явно через `Sentry.captureException`.

### Загрузка source maps во время сборки

Production JavaScript преобразован и минифицирован.
Source maps позволяют сопоставить ошибку с исходным TypeScript/TSX-кодом.

`withSentryConfig` подключает обработку сборки и загрузку карт в GlitchTip.
Для загрузки нужен отдельный API-токен.

DSN не заменяет API-токен:

- DSN нужен приложению для отправки событий;
- API-токен нужен процессу сборки для загрузки артефактов.

Приложение может отправлять ошибки без токена сборки.
Однако для читаемого stack trace нового production-бандла
должны быть доступны соответствующие source maps.

## Назначение файлов

| Файл                                     | Ответственность                                              |
| ---------------------------------------- | ------------------------------------------------------------ |
| `frontend/src/instrumentation-client.ts` | Инициализация браузерного SDK и hook навигации               |
| `frontend/src/instrumentation.ts`        | Серверная точка входа Next.js: `register` и `onRequestError` |
| `frontend/src/sentry.server.config.ts`   | Настройки SDK для Node.js runtime                            |
| `frontend/src/app/error.tsx`             | Резервный UI и отправка ошибок рендера дочерних сегментов    |
| `frontend/src/app/global-error.tsx`      | Глобальный резервный UI, заменяющий корневой документ        |
| `frontend/next.config.ts`                | Интеграция сборки, release и source maps                     |

`instrumentation.ts` и `instrumentation-client.ts` находятся в `src`,
а не внутри `src/app`.

`error.tsx` и `global-error.tsx` — специальные файлы App Router.
В установленной версии Next.js для повторной попытки используется `retry`.

## Локальная настройка

Команды выполняются из `frontend/`, если не указано другое.

Создайте `.env.local` и задайте:

```dotenv
NEXT_PUBLIC_SENTRY_DSN=<DSN frontend-проекта>
NEXT_PUBLIC_SENTRY_ENVIRONMENT=development
```

Пустой или отсутствующий DSN отключает SDK через `enabled: Boolean(dsn)`.

Для обычной разработки API-токен загрузки source maps не нужен.
Если мониторинг локальных ошибок не требуется, оставьте DSN пустым.

DSN и доступ к проекту можно запросить у ответственного за GlitchTip.

После изменения env-переменных перезапустите dev-сервер.
Для production-браузерного кода потребуется новая сборка:
`NEXT_PUBLIC_*` подставляются при `next build`.

## Переменные окружения

| Переменная                       | Назначение                                                       |
| -------------------------------- | ---------------------------------------------------------------- |
| `NEXT_PUBLIC_SENTRY_DSN`         | Адрес отправки событий                                           |
| `NEXT_PUBLIC_SENTRY_ENVIRONMENT` | Метка окружения, например `development`, `staging`, `production` |
| `SENTRY_AUTH_TOKEN`              | Секретный токен для загрузки артефактов                          |
| `SENTRY_ORG`                     | Slug организации                                                 |
| `SENTRY_PROJECT`                 | Slug проекта                                                     |
| `SENTRY_URL`                     | Базовый URL GlitchTip                                            |

Метка `NEXT_PUBLIC_SENTRY_ENVIRONMENT` не равна режиму сборки:
локальная production-сборка может отправлять события с меткой `development`.

Переменные с префиксом `NEXT_PUBLIC_` доступны браузеру.
Нельзя добавлять этот префикс к API-токену.

## Загрузка source maps

Дополните локальное окружение либо окружение CI:

```dotenv
SENTRY_AUTH_TOKEN=<секретный токен>
SENTRY_ORG=robot-warehouse
SENTRY_PROJECT=robot-warehouse-frontend
SENTRY_URL=https://app.glitchtip.com
```

Для проверенной настройки токена используются права:

- Projects → releases (`project:releases`);
- Organization → read (`org:read`).

Полный доступ не требуется.

Выполните:

```bash
pnpm build
```

При наличии токена конфигурация требует также организацию, проект и URL.
Ошибки плагина пробрасываются через `errorHandler`.

После загрузки клиентские source maps удаляются из выходных
артефактов согласно `deleteSourcemapsAfterUpload`.

### Проверка без токена

```bash
SENTRY_AUTH_TOKEN= pnpm build
```

В текущей конфигурации без токена:

- загрузка source maps отключена;
- создание и финализация release отключены;
- сборка должна проходить.

SDK 11.11.0 при этом может выводить:

```text
No auth token provided. Will not create release.
```

В проверенной зависимости проверка токена выполняется до проверки
`release.create`. Поэтому предупреждение возможно даже при `create: false`.
Оно само по себе не означает падение сборки.

## Ручная отправка обработанных ошибок

Наличие `catch` означает, что приложение перехватило исключение,
но не обязательно устранило причину сбоя. Например, интерфейс может
продолжить работу, хотя сохранение карты завершилось неудачно.

Если неожиданная ошибка перехвачена и не будет зарегистрирована
на другом уровне, отправьте её явно через `Sentry.captureException`.
Добавьте безопасный контекст: какую операцию выполняло приложение
и какие технические условия помогут воспроизвести проблему.

Условный пример: `performOperation` обозначает операцию приложения.

```ts
import * as Sentry from "@sentry/nextjs";

try {
  await performOperation();
} catch (error) {
  Sentry.captureException(error, {
    tags: {
      operation: "example.perform-operation",
    },
    extra: {
      source: "manual-catch",
    },
  });

  // Отдельно покажите пользователю понятное сообщение
  // и обработайте неуспешную операцию.
}
```

В реальном коде замените примерные значения контекстом конкретной
операции. `tags` используйте для коротких признаков классификации,
а `extra` — для дополнительных диагностических сведений.

Передавайте исходную ошибку, а не заменяйте её новым исключением
только ради другого сообщения: так сохраняется исходный stack trace.

### Какие ситуации отправлять

- Неожиданные сбои, из-за которых операция не выполнена,
  следует регистрировать, даже если интерфейс обработал их без падения.
- Ожидаемые ошибки валидации, намеренную отмену запроса и другие
  предусмотренные ситуации не следует автоматически считать
  программными сбоями. Необходимость их регистрации определяется
  поведением конкретной операции.

Сам по себе HTTP-статус или наличие `catch` не определяет,
нужно ли отправлять событие.

### Где регистрировать ошибку

Для каждого сценария определите ответственную точку регистрации.
Не отправляйте один сбой вручную одновременно в API-обёртке,
сервисе и компоненте.

Если после `catch` ошибка пробрасывается дальше, учитывайте,
что её может зарегистрировать вышестоящий обработчик или SDK.
Не следует рассчитывать, что автоматическая дедупликация
устранит все повторные события.

### Безопасность контекста

Не прикладывайте к событию целиком запрос, ответ, состояние
приложения или пользовательскую форму.

Добавляйте только необходимые диагностические поля.
Не передавайте пароли, токены, cookies и другие чувствительные
данные через текст ошибки, `tags` или `extra`.

Ограничения автоматического сбора `dataCollection` не заменяют
проверку данных, которые разработчик добавляет вручную.

## Проверка интеграции

Готовый пример находится в
[`examples/monitoring-smoke-test/page.tsx`](examples/monitoring-smoke-test/page.tsx).

Он хранится вне `src/app`, поэтому сам по себе не создаёт
маршрут приложения. Для проверки его нужно временно скопировать
в App Router, а после проверки удалить.

Все команды этого раздела выполняются из `frontend/`.

### Подготовка окружения

В `.env.local` задайте:

```dotenv
NEXT_PUBLIC_SENTRY_DSN=<DSN frontend-проекта>
NEXT_PUBLIC_SENTRY_ENVIRONMENT=monitoring-review
```

DSN и доступ к frontend-проекту GlitchTip запросите
у ответственного за мониторинг.

Для отправки ошибок API-токен не нужен.
Он требуется отдельно для загрузки source maps.

Если DSN отсутствует или пуст, SDK отключён.
Наличие ID события в интерфейсе тестовой страницы само по себе
не подтверждает получение события сервером.

### Временное подключение страницы

Сначала убедитесь, что маршрут `src/app/monitoring-test`
не занят существующей страницей:

```bash
test ! -e src/app/monitoring-test &&
mkdir src/app/monitoring-test &&
cp ../docs/examples/monitoring-smoke-test/page.tsx \
  src/app/monitoring-test/page.tsx
```

Если каталог уже существует, первая команда завершится
неуспешно и копирование не выполнится. Не перезаписывайте
существующий маршрут: сначала проверьте его содержимое.

Тестовую страницу нельзя включать в обычный деплой.

### Проверка отправки браузерных ошибок

Для проверки production-поведения соберите и запустите приложение
без загрузки source maps:

```bash
SENTRY_AUTH_TOKEN= pnpm build &&
SENTRY_AUTH_TOKEN= pnpm start
```

Перед запуском остановите другой экземпляр frontend,
если он использует тот же порт.

Откройте `/monitoring-test` на адресе запущенного приложения.

Нажимайте кнопки по очереди, проверяя результат после каждой:

| Кнопка                              | Ожидаемый результат                                                                                                    |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Отправить обработанную ошибку       | В GlitchTip появляется событие с текстом `Monitoring smoke test: handled error`; страница остаётся работоспособной     |
| Вызвать необработанную ошибку клика | В GlitchTip появляется событие с текстом `Monitoring smoke test: unhandled click error`                                |
| Вызвать ошибку рендера              | Появляется резервный интерфейс из `error.tsx`, а в GlitchTip — событие с текстом `Monitoring smoke test: render error` |

Ошибку рендера проверяйте последней: она заменяет тестовую
страницу резервным интерфейсом. Для возвращения к тестовым
кнопкам заново откройте маршрут с полной загрузкой страницы.

В GlitchTip выберите проект `robot-warehouse-frontend`,
проверьте временной диапазон и фильтр окружения
`monitoring-review`. Откройте именно новое событие:
ошибки с одинаковым сообщением могут объединяться
в существующую группу.

Оставляйте страницу открытой после нажатия кнопки,
чтобы SDK успел отправить событие.

Три кнопки не проверяют серверный перехват Next.js,
NestJS, Edge runtime или `global-error.tsx`.

### Если событие не появилось

Проверьте:

1. DSN задан до сборки и относится к нужному проекту.
2. Запущена новая сборка с тестовой страницей.
3. В GlitchTip выбраны правильный проект, окружение
   и временной диапазон.
4. Во вкладке Network браузера появился запрос отправки
   события в GlitchTip; проверьте его статус.
5. Запрос не блокируется расширением браузера
   или сетевыми ограничениями.

После изменения `NEXT_PUBLIC_*` production-приложение
нужно пересобрать: эти значения встраиваются
в браузерный код при `next build`.

### Проверка диагностического контекста

В DevTools откройте Network и найдите запрос отправки
тестового события. Проверьте его payload, затем сравните
с сохранённым событием в GlitchTip.

Проверьте наличие значения `User-Agent` и сведений
о браузере и ОС. Значения прочих заголовков
не должны передаваться этим allow-list.

Для проверки ограничений используйте только выдуманные
маркеры, не настоящие пароли, токены или персональные данные.

Содержимое исходящего запроса и сохранённого события
может отличаться: принимающий сервис может добавлять
собственные данные.

### Проверка source maps

Остановите локальный сервер. Пока тестовая страница
ещё подключена, настройте переменные из раздела
«Загрузка source maps» и выполните:

```bash
pnpm build && pnpm start
```

В этом случае `SENTRY_AUTH_TOKEN` должен быть непустым
и доступным процессу сборки.

1. Убедитесь, что загрузка карт завершилась без ошибки.
2. Откройте тестовую страницу именно этой сборки.
3. Вызовите новую тестовую ошибку.
4. Откройте новое событие в GlitchTip.
5. Проверьте исходный TSX-файл, строку и окружающий код.

Сообщение об успешной загрузке карт само по себе
не подтверждает правильное восстановление исходников.

### Удаление временной страницы

Остановите локальный сервер и выполните:

```bash
rm src/app/monitoring-test/page.tsx
rmdir src/app/monitoring-test
```

`rmdir` удалит каталог только в том случае, если он пуст.
Если в нём остались другие файлы, сначала проверьте их;
не используйте рекурсивное удаление наугад.

Удаление исходника не удаляет маршрут из уже готовой
production-сборки. Перед обычным запуском или деплоем
нужна новая сборка без тестовой страницы:

```bash
SENTRY_AUTH_TOKEN= pnpm build
```

После удаления страницы проверьте состояние репозитория:

```bash
git status --short
```

Временный маршрут не должен попасть в коммит.
Шаблон в `docs/examples/monitoring-smoke-test/`
остаётся в репозитории для следующих проверок.

### Отдельная проверка серверных ошибок Next.js

Браузерный пример не проверяет `onRequestError`.

При `cacheComponents: true` тестовый GET-обработчик может
выполниться во время сборки. Для ранее проведённой проверки
ошибки именно по запросу использовался `await connection()`
перед намеренным `throw`.

Готовый серверный пример в этот smoke test не входит.

## Безопасность и пользовательские данные

`.env.local` не должен отслеживаться Git.

Проверка из корня репозитория:

```bash
git check-ignore -v -- frontend/.env.local
git ls-files -- frontend/.env.local
```

Первая команда должна показать правило игнорирования.
Вторая не должна ничего вывести.

API-токен нельзя публиковать в репозитории, чатах, скриншотах и логах.
При раскрытии токен необходимо отозвать и заменить.

SDK настроен с ограничениями `dataCollection`.

В браузерной конфигурации разрешена передача значения заголовка
`User-Agent` для диагностики браузера и операционной системы.
Значения остальных request headers не разрешены этим списком;
сбор response headers отключён. Имена отфильтрованных заголовков
могут сохраняться в событии.

В серверной конфигурации автоматический сбор HTTP-заголовков
пока отключён. Необходимые серверные заголовки следует включать
отдельно после определения безопасного списка.

Автоматический сбор cookies и тел HTTP-запросов отключён.
Сбор query params пока отключён: разрешённый список следует
определить по фактически используемым параметрам приложения.

Эти ограничения не гарантируют отсутствие любых чувствительных
данных: они могут оказаться, например, в тексте ошибки
или вручную добавленном контексте.

### Данные запросов к БД

`databaseQueryData: false` ограничивает автоматическую передачу
данных, связанных с запросами к БД, в поддерживаемых интеграциях.
Например, значения фильтров и данные записи могут содержать
персональные сведения.

Этот параметр не отключает саму инструментацию БД и не запрещает
передачу параметризованного текста запроса и структурных метаданных,
таких как операция и таблица.

Однако наличие этой настройки не означает, что сбор запросов
уже подключён: для этого нужны соответствующая интеграция
и настройки мониторинга.

Текущий серверный SDK работает в процессе Next.js.
Он не подключает мониторинг отдельного NestJS backend.

В проверенном браузерном envelope поле `user.ip_address` отсутствовало,
но присутствовало в сохранённом GlitchTip событии.
Полное удаление IP на стороне сервиса не подтверждено.

При настройке дополнительных контекстов повторно проверяйте
фактическое содержимое отправляемых событий.

## Что нужно для CI и деплоя

Автоматическая загрузка в CI пока не подключена этой задачей.

Ответственному за сборку необходимо:

- передать `SENTRY_AUTH_TOKEN` через секреты CI;
- задать `SENTRY_ORG`, `SENTRY_PROJECT`, `SENTRY_URL`;
- передать публичные DSN и метку окружения до `next build`;
- проверить загрузку карт и новое событие на стенде;
- использовать на стенде артефакты той сборки, для которой загружены карты.

API-токен нужен сборке, а не браузеру.

## Проведённые локальные проверки

В рамках настройки вручную проверены:

- отправка обработанной браузерной ошибки;
- сбор необработанной ошибки обработчика клика;
- отправка ошибки React-рендера через `error.tsx`;
- работа `global-error.tsx` при отсутствии ближайшего `error.tsx`;
- серверная ошибка Next.js Route Handler;
- загрузка source maps и восстановление исходного TSX;
- сборка без токена;
- чистая сборка после удаления тестовых маршрутов.

Это ручные проверки, а не автоматизированные тесты.

Ошибку непосредственно корневого layout отдельно не воспроизводили.
Работа на развёрнутом стенде и автоматизация CI ещё не проверены.
