# Диспетчер sim-engine

Статус: согласуемая модель. Общий протокол и цикл находятся в [sim-engine](sim-engine.md), модель актора — в [robot](robot.md).

## Граница ответственности

Диспетчер выполняется на бэкенде, внутри серверного sim-engine. Диспетчер и все акторы роботов одного запуска находятся в одном процессе — на инстансе, владеющем симуляцией склада. Ссылки на акторов, очередь намерений, снимки для расчёта и резервации хранятся в памяти этого процесса.

Диспетчер управляет очередью заданий, рассчитывает маршруты, проверяет намерения всех роботов и разрешает шаги. Он не записывает координаты напрямую в робота. Принятое назначение, маршрут и текущая позиция принадлежат актору.

Ссылки `robots` указывают на акторов из долгоживущего серверного реестра. Остановка или сброс запуска не удаляет их; существующие роботы получают акторов при старте процесса. Отдельная серверная операция `robot.delete` удаляет доменного робота и его актор по [правилам жизненного цикла](robot.md#жизненный-цикл). Диспетчер согласует отсутствие назначения, намерений и резерваций перед удалением. Эта операция адресована роботу, а не конкретному запуску, и проходит проверку прав на сервере.

Намерения и результаты поступают от серверных акторов через внутренние события. Команды пользователя поступают из HTTP/WebSocket-слоя бэкенда после проверки прав. Клиент не имеет прямого доступа к методам диспетчера и не присылает решения о движении. Публичный снимок преобразуется серверным адаптером в DTO для клиентов; ссылки на акторов и внутренние структуры не передаются в браузер.

## Модель данных

```ts
type DispatcherState = {
  runId: RunId;
  layout: Layout;
  nextTickId: TickId;
  status: "ready" | "running" | "paused" | "stopped" | "faulted";

  robots: Map<RobotId, RobotActorRef>;
  tasks: Map<TaskId, TransportTask>;
  taskQueue: TaskId[];
  pendingCommands: EngineCommand[];
  commandLedger: Map<CommandId, { status: "pending" | "applied" | "rejected" }>;
  lastDeliveredTick: Map<RobotId, TickId>;
  nextStatusPollTick: TickId;
  pendingStatusPolls: Map<RobotId, { requestedAtTick: TickId; deadlineTick: TickId }>;
  robotChecks: Map<RobotId, { sinceTick: TickId; reason: "missingStatus" | "movingWithoutIntent" }>;

  intentInbox: IntentInbox;
  frame: DispatchFrame | null;
};

type IntentInbox = {
  intents: Map<RobotId, MoveIntent>;
};

type TransportTask = {
  id: TaskId;
  pickupStationId: StationId;
  dropoffStationId: StationId;
  status: "queued" | "assigned" | "inProgress" | "done" | "failed";
  assignedRobotId: RobotId | null;
  createdAtTick: TickId;
  failureReason: string | null;
};

type DispatchFrame = {
  tickId: TickId;
  snapshots: Map<RobotId, RobotSnapshot>;
  statuses: Map<RobotId, RobotStatusEvent>;
  occupancy: Map<CellKey, RobotId>;
  intents: Map<RobotId, MoveIntent>;
  decisions: Map<RobotId, MoveDecision>;
  deliveredDecisions: Set<RobotId>;
  reservedCells: Map<CellKey, RobotId>;
  reservedEdges: Map<EdgeKey, RobotId>;
  results: Map<RobotId, MoveResult>;
  waitFor: Map<RobotId, RobotId[]>;
};
```

`Layout` содержит размеры поля, препятствия, станции и версию. Общие идентификаторы и позиции описаны в `sim-engine`. `RobotActorRef`, `RobotSnapshot`, ключи клеток и рёбер — концептуальные типы.

`occupancy` строится из снимков акторов. `frame` существует только для обработки текущего тика. Очередь внешних команд отделена от ограниченной очереди намерений. Порядок прихода намерений не используется как приоритет.

## Методы

Журнал очереди и дедупликации диспетчера отделён от лога робота: робот самостоятельно журналирует фактическое получение и результат обработки каждой доставленной команды. Этот лог не переносит владение очередью команд к роботу.

Все адресные команды актору содержат `robotId`, даже при доставке через ссылку на актор. Диспетчер выбирает ссылку по ID, актор независимо проверяет адресата.

| Метод | Ответственность |
|---|---|
| `enqueueCommand(command)` | Проверить принадлежность запуску и поставить внешнюю команду в очередь |
| `receiveIntent(intent)` | Проверить регистрацию робота, актуальность и отсутствие другого ожидающего намерения; поставить в очередь |
| `receiveRobotEvent(event)` | Обработать подтверждение или результат актора в текущей фазе |
| `deliverTick(tickId)` | Доставить событие общих часов каждому роботу не более одного раза, отметив доставку до отправки |
| `deduplicateCommand(command)` | До постановки команды в очередь проверить commandId, включая ещё не подтверждённые команды; повтору вернуть текущий или сохранённый результат |
| `pollRobotStatuses(tickId)` | Каждые 100 тиков запросить статус всех роботов; зарегистрировать ожидаемые ответы и их сроки |
| `requestRobotStatus(robotId, tickId)` | Внеочередно запросить статус при новом задании, отмене текущего или диагностике; согласовать запрос с уже ожидаемым ответом |
| `validateRobotReports(frame)` | Проверить поступившие изменения, ответы на опросы, сроки и согласованность намерений; статус на каждом тике не требуется |
| `checkRobot(robotId, reason)` | Запретить шаг, запросить статус, сверить снимок и зафиксировать ошибку; в MVP приостановить запуск |
| `tick()` | Выполнить полный цикл без перекрытия с другим тиком |
| `getSnapshot()` | Собрать публичное состояние из заданий и снимков акторов |
| `takeIntentBatch()` | Атомарно отделить набор текущего тика от очереди новых намерений; обработать не более одного намерения каждого робота |
| `applyPendingCommands()` | Последовательно применить команды до расчёта движения |
| `readRobotSnapshots()` | Прочитать согласованное состояние акторов |
| `buildOccupancy(snapshots)` | Получить индекс занятых клеток |
| `validateIntent(intent, snapshot)` | Проверить позицию, соседство, маршрут, версию, границы и возможность движения |
| `resolveIntents(frame)` | Разрешить конфликты и создать резервации |
| `deliverDecisions(frame)` | Передать решения акторам и обработать результаты |
| `advanceService()` | Продвинуть погрузку/выгрузку подходящих роботов на один тик |
| `updateTasks(events)` | Обновить глобальные задания по событиям роботов |
| `assignTasks()` | Предложить задания свободным исправным роботам и обработать ответы |
| `planRoute(robot, target)` | Найти маршрут до цели |
| `replaceRoute(robotId, route)` | Предложить новую версию маршрута и обработать ответ |
| `detectDeadlocks(frame)` | Найти циклы ожидания и сформировать событие |

Метода `collectIntents()` нет: намерения поступают по инициативе акторов.

Контроль очередей заданий и команд и отсутствие дублей — ответственность диспетчера. `commandLedger` хранит состояние обработки и результат подтверждения на срок допустимой повторной доставки; приведённый тип показывает минимальную модель состояний, конкретные поля результата зависят от команды. Повтор не направляется роботу, даже если оригинал ещё ожидает подтверждения. `lastDeliveredTick` не сбрасывается при смене запуска: номера тиков монотонны в течение жизни акторов. `deliveredDecisions` запрещает повторную отправку решения в текущем тике; ответы прошлых тиков отклоняются. Повторы входящих намерений и подтверждений также не должны повторно менять очередь, задания или резервации.

Перед доставкой тика или решения отметка фиксируется в диспетчере. Ошибка доставки в одном процессе считается ошибкой запуска и не вызывает слепую повторную отправку. Внутренние состояния и `pendingMove` остаются проверками корректности робота, а не его собственным механизмом ведения очереди и журнала дублей.

Роботы публикуют статус при смене состояния и в ответ на запрос. Каждые 100 тиков диспетчер опрашивает всех зарегистрированных роботов, включая moving, paused и stopped. Отсутствие спонтанных сообщений на обычном тике не является ошибкой. Проверяются сроки ответов, актуальность тика опроса, наличие намерения после фазы подготовки в atWaypoint/awaitingPermission и срок уже начатого перехода moving. Подробности — в [полной модели робота](robot.md#публикация-состояния-и-контрольный-опрос).

При получении нового задания диспетчер может вне очереди опросить кандидатов на назначение, при отмене — назначенного робота. Это не переносит плановый опрос. На робота допускается один ожидаемый запрос статуса; совпавшие причины объединяются. Если после управляющей команды требуется новый ответ, прежний запрос закрывается, а новый получает другой тик. В одном тике два разных запроса одному роботу не отправляются. Запрос статуса не заменяет остановку и не подтверждает отмену задания.

## Правила назначения и маршрутизации

- Начальный выбор: FIFO заданий, ближайший доступный робот по длине достижимого пути; равенство разрешается стабильным правилом по ID.
- Пока принятие назначения не завершено, задание нельзя предложить второму роботу. Отказ возвращает его в очередь; причина отказа сохраняется в событии.
- Поиск пути учитывает стены, сломанных роботов и текущие позиции свободных роботов как препятствия для конкретного расчёта. Свободный робот может уехать позже, поэтому временная блокировка не равна окончательной недостижимости.
- Позиции движущихся роботов учитываются при разрешении шага; предварительная оптимизация пересечений всех маршрутов не требуется.
- Статическую недостижимость проверяют отдельно от динамической занятости. Временно занятая станция не делает задание окончательно ошибочным.
- После погрузки диспетчер строит путь к станции выгрузки и заменяет маршрут внутри назначения.

## Правила разрешения движения

1. Намерение действительно только для текущего запуска, позиции и версии назначения. Номер тика назначается при извлечении из очереди.
2. Препятствия и границы запрещают шаг.
3. В первой версии клетка, занятая в начале тика, недоступна для входа, даже если другой робот собирается её освободить.
4. Из нескольких претендентов на свободную клетку выбирается один по стабильному приоритету: длительность ожидания, затем ID. Это правило само по себе не гарантирует отсутствия голодания.
5. Встречный обмен клетками запрещён. Резервируются целевая клетка и переход.
6. После разрешения диспетчер ждёт результата актора в фазе исполнения. Резервация не освобождается для повторного назначения в том же тике.
7. После нескольких отказов диспетчер пробует альтернативный маршрут. Отступление также требует обычных намерений и разрешений.
8. Цикл ожиданий формирует `dispatcher.deadlock.detected`. Автоматическое разрешение всех дедлоков не является обязательным для первой версии.

## Инварианты

- Диспетчер не изменяет `robot.position`.
- В очереди сохранено не более одного намерения от зарегистрированного робота; её размер не превышает число роботов. Зафиксированный набор текущего тика хранится отдельно и также ограничен числом роботов.
- Новое намерение после обработки результата или замены маршрута не включается повторно в уже зафиксированный набор текущего тика.
- Одному заданию назначен не более чем один робот; одному роботу — не более одного задания.
- Следующий тик начинается после завершения предыдущего.
- Пауза и поломка применяются на границе фаз, до выдачи разрешений. Команда, поступившая во время исполнения, ожидает следующей границы.
